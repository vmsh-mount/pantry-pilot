What changes

=
Computation ships per the PRD (utils/nutrition_targets.py · personalised_weekly_targets) — this plan doesn't fork it.
+
Add GET /v1/nutrition/targets — the per-member breakdown, built by itemizing the PRD function's helpers.
+
New UI: a per-member breakdown in Settings, with a role-fallback badge when biometrics are missing.
≠
The per-order NutritionCard hardcode is a separate surface the PRD leaves alone — realign later, not a blocker here.

No new data collection — the fields already exist on household_members. This is the smallest change with the widest downstream effect: every bar, dot, and gap becomes personal.

What changes

+
Reuse the existing MacroBar component, now pointed at the personalized weekly target instead of a constant.
+
Add a "Flagged this week" block driven by the gap diff — semantic amber/red chips, not the brand green, so attention reads at a glance.
+
Diet-aware: watch nutrients keyed off diet_type surface deficiencies a calorie counter can't — the differentiator.
+
Sodium reads as a ceiling, not a goal — amber headroom bar with a limit cap and "under limit ✓", so a near-full bar never looks like progress.
−
No Fat/Carb bars. Phase A computes only calories, protein, fibre and the sodium ceiling; a macro-split target isn't in scope, so the digest doesn't draw one.
+
Coverage guard. B12 and vitamin D come only from the LLM path — never OFF or USDA. "No data" isn't "no intake", so a deficiency only fires above a coverage threshold; below it the digest says not enough data.

The single call-to-action hands straight to Section C. The digest never dead-ends on a number.

B

Gap → Cart — the loop closes

Each shortfall resolves to real, in-stock SKUs: the learned nutrient_food_candidate map picks the food, live Swiggy search prices it, and the top few are nutrition-resolved and ranked by nutrient-per-rupee — filtered by diet and allergies. One tap drops them into the basket.

What changes

+
New GET /v1/nutrition/gaps — gap diff → candidate map → live Swiggy search → resolve top 5 → rank.
+
Reuse the confidence badges from NutritionCard — a recommendation is honest about whether it's label-backed or an estimate.
+
Add-to-cart routes to POST /v1/basket/add-item only when an awaiting_confirmation LoopRun is open; otherwise (the usual case when reading a digest) it adds to a Quick Order so the action never dead-ends. The next order's order_nutrition closes the loop.
+
Signals shown: reordered 6× is the learned repurchase_rate; "best per ₹" is nutrient_per_rupee computed at request time from the live price, never stored. These come from data, not a static list.

This is the piece no retrospective tracker can build: it doesn't just name the gap, it puts the fix in the cart.

Why this is the USP. MyFitnessPal can detect the same protein gap — and then it shows you a number. PantryPilot detects it and drops the paneer in your basket, because it owns purchase history, the nutrition chain, catalog search, and the cart. The mockups above are three screens of one closed loop.
